# ThermalView 개발 지시서

작성 2026-11-22. 근거 문서: [feasibility.md](feasibility.md).
이 문서는 사람 개발자와 코딩 에이전트가 같은 기준으로 작업하기 위한 지시서입니다. 설계 결정이 바뀌면 이 문서를 먼저 고치고 코드를 바꿉니다.

## 1. 목표와 범위

**목표:** PureThermal + 셔터 없는 FLIR Lepton 3.5를 위한 Windows용 실시간 열화상 뷰어·측정 도구. 단일 실행 파일(`thermalview.exe`)로 배포합니다. 단계 9부터 Thermal Master P3(256×192)도 지원합니다.

**1차 범위(MVP):**

| ID | 기능 | 완료 기준 |
| --- | --- | --- |
| F1 | Y16 실시간 수신 | 160×120 Y16을 초당 8.5장 이상으로 받는다 |
| F2 | 팔레트 표시 | Ironbow, Rainbow, Grayscale, White-hot, Black-hot 중 선택해 표시 |
| F3 | 눈금 범위 | 자동(프레임 최소·최대) / 수동(사용자 고정값). 색 막대에 온도 표시 |
| F4 | 최고·최저·중앙점 표시 | 영상 위 표식과 수치 |
| F5 | Spot 측정 | 클릭으로 측정점 추가·삭제, 3×3 평균 온도 표시 |
| F6 | Lepton 제어 | FFC 실행(렌즈 가림 확인), FFC 셔터 모드(MANUAL/AUTO/EXTERNAL), 상태 표시(FPA 온도, 마지막 FFC 이후 시간) |
| F7 | 설정 유지 | 셔터 모드·팔레트·범위·측정점을 저장, 시작 시 복원, 셔터 모드는 주기적으로 재적용 |
| F8 | 연결 감시 | 2초간 프레임이 없으면 스트림 재시작, 실패 시 재연결 루프와 "USB를 다시 꽂으세요" 안내 |
| F9 | 스냅샷 | 컬러 PNG + 온도 원본(16비트 PNG, 단위 0.01 K) + JSON 메타 |

**2차 이후:** Box/Line 측정, 히스토그램, 시간-온도 그래프, 측정표 CSV, 온도 시퀀스 녹화·재생, MP4, 온도 경보, 원격 제어(TCP), 보정, 웹캠 합성, Thermal Master P3(단계 9). 그 밖의 타사 카메라와 제조사 파일 형식은 범위 밖입니다.

## 2. 확정된 기술 결정

| 항목 | 결정 | 이유 |
| --- | --- | --- |
| 언어·툴체인 | Rust stable, `x86_64-pc-windows-msvc` | 개발 PC 기본 툴체인. MinGW 불필요 |
| UI | `eframe`/`egui` 0.37 (기본 wgpu 렌더러) | 검토 결과. 0.37부터 `App::ui(&mut self, ui, frame)`와 `egui::Panel::left/top/bottom` API를 씀. 어댑터는 DX12 → Vulkan → 기타 순으로 고름(`src/main.rs`): Intel Iris Xe에서 wgpu 기본 선택인 Vulkan은 창이 흰색으로만 보였고 DX12는 정상(2026-11-27). `WGPU_BACKEND`로 여전히 강제할 수 있음 |
| 창 시스템 | `crates/winit`: winit 0.30.13에 DPI 패치 1건 적용(`[patch.crates-io]`) | 배율이 다른 모니터로 끌면 창이 커지며 넘어가지 못하는 버그. 수정이 winit 0.31에만 있고 eframe 0.37은 0.30을 씀. eframe이 winit 0.31 이상을 쓰면 제거(`crates/winit/PATCHES.md`) |
| 영상 수신 | 방식 1: 패치한 libuvc를 `cc`로 정적 빌드해 FFI | Windows에서 검증된 경로 |
| libusb | `libusb1-sys`의 `vendored` 기능(정적 링크) | DLL 배포 불필요 |
| P3 수신 | `rusb` 0.9(MIT, 같은 `libusb1-sys` 위의 안전 래퍼)로 제조사 전용 제어·bulk 전송 | 새 `unsafe` 없이 libusb를 씀. P3는 UVC가 아니라 libuvc를 쓸 수 없음 |
| pthread | `crates/libuvc-sys/compat/pthread.h` 자체 shim(Win32 SRWLOCK + CONDITION_VARIABLE) | libuvc가 쓰는 함수가 13개뿐 |
| 바인딩 | 손으로 쓴 최소 FFI(`bindgen` 미사용) | libclang 설치 의존 제거 |
| 설정 저장 | `serde` + JSON, `%APPDATA%\thermalview\config.json` | 이식성, 사람이 읽을 수 있음 |
| 이미지 저장 | `image` (PNG 8비트 컬러, 16비트 그레이) | 16비트 PNG로 온도 원본을 손실 없이 저장 |
| 동영상(MP4) | Windows 내장 Media Foundation H.264 인코더(`windows` 크레이트, `src/video/mf.rs`). 글자는 `ab_glyph`로 Windows 글꼴을 그림 | DLL 동봉·라이선스·특허 부담 없음. FFmpeg+x264는 앱 전체가 GPL이 되고, OpenH264는 소스 빌드 시 특허 비용이 면제되지 않음 |
| 웹캠 | Media Foundation Source Reader(`windows` 크레이트, `src/webcam/mf.rs`) | MP4와 같은 Windows 기능이라 새 의존성이 없음. `nokhwa` 등은 같은 API를 감싸면서 크레이트가 많이 늘어남 |
| 라이선스 | **미정**. 결정 전까지 GPL 코드(thermal-cat 등)는 복사하지 않는다 | 사용자 결정 사항 |

방식 3(nokhwa/Media Foundation, Zadig 불필요)은 MVP 이후 별도 실험으로 검증합니다. 캡처 계층은 `trait`로 분리해 나중에 백엔드를 추가할 수 있게 합니다.

## 4. 하드웨어 규칙 (반드시 지킬 것)

이 규칙들은 실제 장비 디버깅에서 나온 것입니다. 어기면 재현하기 어려운 오류가 납니다.

1. **WinUSB 단독 점유.** 장치는 한 프로세스만 열 수 있습니다. GetThermal 등 다른 프로그램이 열려 있으면 `uvc_open`이 실패하므로 "다른 프로그램이 카메라를 사용 중" 메시지를 보여 줍니다. USB 문자열(제조사, 제품, 시리얼=펌웨어 버전)은 `uvc_open` **전에** `uvc_get_device_descriptor`로 읽습니다.
2. **claim 후 probe.** vendor libuvc의 `uvc_get_stream_ctrl_format_size`는 스트리밍 인터페이스를 먼저 claim하도록 패치되어 있습니다. 이 패치를 되돌리지 않습니다. libuvc를 갱신할 때는 `vendor/libuvc/PATCHES.md`의 변경을 다시 적용합니다.
3. **실패한 시작 후 핸들 유지.** `uvc_start_streaming`이 실패해도 곧바로 `uvc_close`하지 않습니다(GetThermal에서 크래시 원인). 정리는 Handle의 `Drop` 한 곳에서만 합니다.
4. **셔터 없음.** 기본 셔터 모드는 MANUAL입니다. FFC 버튼은 "렌즈를 가렸습니까?" 확인 후에만 명령을 보냅니다. AUTO를 고르면 잔상 경고를 표시합니다.
5. **설정 재적용.** Lepton은 리셋되면 AUTO로 돌아갑니다. 저장된 셔터 모드를 연결 직후와 5초마다 읽어 비교하고, 다르면 다시 씁니다(read-modify-write, 32바이트 객체 중 `shutterMode`만 변경).
10. **스트리밍 중 CCI 명령 최소화.** PureThermal은 Lepton 명령(XU 요청)을 처리하는 동안 영상 프레임을 놓칩니다. 실측: 명령 없이 8.77 fps, 1초마다 4개 명령이면 8.1~8.3 fps(불량 프레임 0, 프레임이 통째로 빠짐). 그래서 상태 폴링은 5초마다 2개(FPA 온도, 셔터 모드 객체)로 제한했고, 이때 8.77 fps로 명령이 없을 때와 같습니다(30초 측정). 또 fps는 USB 요청 없이 프레임 카운터로 계산합니다. 새 상태 항목을 추가할 때는 이 예산을 지킵니다.
11. **제어 전송 타임아웃.** libuvc 원본은 제어 전송 타임아웃이 0(무한)이라, 펌웨어가 응답하지 않으면 스레드와 프로세스 종료가 영원히 멈추고 프로세스가 커널에 남아 장치를 붙잡았습니다(USB 재연결 전까지 `Access denied`). vendor libuvc에 2초 타임아웃을 넣었습니다(`PATCHES.md` 3번).
6. **XU 명령 매핑.** unit = 모듈(명령ID & 0x3F00): AGC 0x0100→3, SYS 0x0200→6, VID 0x0300→7, OEM 0x0800→4, RAD 0x0E00→5. control = ((명령ID & 0xFF) >> 2) + 1. Lepton enum/bool은 전송 시 4바이트. "run" 명령은 control 번호 1바이트를 SET_CUR로 보냅니다.
7. **온도 변환.** 연결 시 RAD TLinear 활성(0x4EC0)과 해상도(0x4EC4: 0=0.1 K, 1=0.01 K)를 읽습니다. TLinear가 꺼져 있으면 "원시값(온도 아님)"을 표시하고 모든 측정값을 `cnt` 단위로 보여 줍니다. 섭씨 = raw × 해상도 − 273.15. 이 값에 앱의 온도 보정(단계 5)을 더하며, 온도 변환은 `ThermalFrame::value`/`value_f`/`raw_from_value` 한 곳에서만 합니다.
8. **USB 제어와 스트림의 동시성.** XU 명령은 스트리밍 중에도 같은 핸들로 보냅니다. 모든 USB 호출(스트림 시작·정지, XU 명령)은 카메라 작업 스레드 하나에서만 하고, UI는 명령 채널(`Command`)로 요청합니다. 그래서 잠금 없이 직렬화됩니다.
9. **스트림 정지 대응.** 첫 프레임은 8초(Lepton 부팅 대기), 그 뒤로는 2초 동안 프레임이 없으면 장치를 닫고 1초 뒤 다시 엽니다. 3회 연속 프레임을 못 받거나 USB 전송이 끝나지 않으면(`has_stuck_transfers`) USB 재연결 안내를 띄웁니다. "수신 중" 표시는 프레임이 실제로 도착한 뒤에만 합니다. USB 종료 경로를 고치면 `examples/churn`을 디버거 아래에서 돌려 힙 손상이 없는지 확인합니다(`PATCHES.md` 4~9번).

## 5. 스레드와 데이터 흐름

- **libuvc 콜백 스레드:** 프레임 크기(38,400바이트)와 형식을 확인하고 `Vec<u16>`으로 복사해 프레임 대기열(최대 16장, 약 1.8초, 넘치면 가장 오래된 것을 버림)에 넣은 뒤 `egui::Context::request_repaint()`를 호출합니다. 콜백 안에서는 할당 외의 무거운 일을 하지 않습니다.
- **카메라 작업 스레드(`camera/worker.rs`):** 연결·재연결, 타임아웃 감지, 셔터 모드 재적용, 상태 폴링(1초 간격 FPA 온도 등), UI 명령 실행.
- **UI 스레드:** 두 단계로 나눕니다.
  - `App::logic`(`ThermalApp::tick`): 대기열의 프레임을 오래된 것부터 모두 꺼내 통계·보정·팔레트 변환, CSV·녹화·그래프 기록, 경보 판정, 원격 명령 처리, 설정 저장을 합니다. eframe은 창이 최소화되거나 그려지지 않을 때 `ui`를 건너뛰고 `logic`만 부르므로(숨은 창은 초당 약 10회), 이 일들은 반드시 여기서 합니다. 프레임 시각은 처리 시각이 아니라 도착 시각(`captured`)으로 계산합니다.
  - `App::ui`: 화면만 그립니다. 텍스처 업로드(`TextureHandle::set`, NEAREST 필터)도 여기서만 합니다. 숨은 창에서 올린 텍스처 변경은 전달되지 않고 쌓이기 때문입니다.
  - 프레임이 없어도 상태 갱신을 위해 0.5초마다 다시 실행합니다.
- **원격 제어 스레드(`remote/server.rs`):** 수신 스레드 1개와 연결마다 스레드 1개. 명령 줄을 해석해 채널로 UI 스레드에 넘기고 `request_repaint()`로 깨운 뒤 응답을 기다립니다(최대 3초). 앱 상태는 UI 스레드만 만지므로 잠금이 없습니다.
- **저장:** 스냅샷 파일 3개는 합쳐 50 KB 정도라 UI 스레드에서 바로 씁니다. 시퀀스 녹화(단계 3)는 별도 스레드로 합니다.
- **MP4 쓰기 스레드(`video/mod.rs`):** UI 스레드는 프레임마다 컬러 영상과 표식 목록(`Scene`)만 보내고, 그리기·NV12 변환·인코딩은 이 스레드가 합니다. COM과 Media Foundation 객체는 이 스레드에서 만들고 이 스레드에서만 씁니다.
- **웹캠 수신 스레드(`webcam/mod.rs`):** 합성을 켰을 때만 1개. 장치를 열고 프레임마다 RGBA 변환과 윤곽 계산을 한 뒤 최신 1장을 `Arc`로 바꿔 넣고 `request_repaint()`를 부릅니다. UI는 `ui`에서 이 영상을 텍스처로 올리고, MP4에는 같은 `Arc`를 넘깁니다. 끌 때는 정지 표시 후 최대 2초 기다립니다.

## 6. 단계별 작업

### 단계 1 — 기술 검증 (관문: 초당 8.5장 이상)

### 단계 5 — 온도 보정

카메라의 TLinear 값은 방사율 1인 물체(흑체)로 가정한 **겉보기 온도**입니다. 앱이 이 값 위에 보정을 계산해 표시합니다. 카메라 설정과 원본 값은 바꾸지 않습니다.

| 항목 | 기준 |
| --- | --- |
| 적용 위치 | 소프트웨어. `ThermalFrame::value`를 거치는 모든 값(최고·최저·평균·중앙, Spot, Box/Line, 히스토그램, 그래프, 경보, CSV, 스냅샷 JSON)에 적용. 원시값, 16비트 PNG, `.tvseq`는 보정 전 값을 유지하고, 재생할 때는 현재 보정을 적용 |
| 계산 순서 | 1) 기준점 보정: 겉보기' = 기울기 × 겉보기 + 오프셋. 2) 방사율: 8~14 µm 대역 복사량 L로 L(겉보기') = ε·L(물체) + (1−ε)·L(반사)를 풀어 물체 온도를 구함 |
| 방사율 | 0.10~1.00, 기본 1.00. 재질 예시 목록 제공. 1.00이면 반사 온도는 쓰지 않음 |
| 반사 온도 | 물체에 비치는 주변 온도, 기본 20 °C |
| 기준점 보정 | 온도를 아는 기준체를 중앙 또는 Spot으로 재어 최대 2점 기록. 1점이면 오프셋만, 2점이면 기울기와 오프셋. 기록할 때 기준 온도를 현재 방사율 모델에 넣어 기대 겉보기 온도를 구하고, 실시간 프레임 16장(약 2초)의 보정 전 평균과 짝지음. 두 점은 측정값이 2 °C 이상 떨어져야 하고 기울기는 0.5~2.0이어야 함 |
| 계산 방식 | 대역 복사량은 Planck 식을 100~2500 K 구간에서 0.5 K 간격으로 적분한 표(최초 1회). 보정을 바꾸면 원시값 65,536개에 대한 온도표를 다시 만들고, 프레임에는 이 표를 공유 참조로 붙임. 보정이 없으면 표 없이 기존 선형 변환 |
| 범위 밖 | 계산된 복사량이 표 범위를 벗어나면 표 끝 온도로 제한 |
| 제약 | TLinear가 꺼져 있으면 보정하지 않음. CSV 기록 중에는 한 파일 안의 값이 섞이지 않도록 보정을 바꿀 수 없음 |
| 표시 | 보정이 켜져 있으면 측정 영역에 적용 중인 값을 표시. 스냅샷 JSON에 보정 설정을 기록 |
| 카메라 내부 방사율 | 연결할 때 RAD Flux Linear 파라미터(0x4EBC)를 한 번 읽음(폴링 예산과 무관). 카메라 쪽 방사율이 1이 아니면 앱 보정과 겹친다고 경고 |

구현: `thermal/calibration.rs`(계산, 단위 테스트), `app/calibration.rs`(화면). 대기 투과율과 거리 보정은 범위 밖입니다(근거리 실내 측정 기준).

2026-11-24 실제 카메라 확인: 연결 시 카메라 내부 방사율 1.000을 읽고 8.93 fps를 유지했습니다. 실제 프레임에 ε 0.95, 반사 20 °C, 기준 1점(+0.5 °C)을 적용하면 중앙 32.79 → 33.42 °C, 최고 43.47 → 44.58 °C로 식과 일치했고, 원시값 역변환도 같은 값으로 돌아왔습니다. 온도표 생성 2.4 ms, 화소별 조회 0.016 ms/프레임입니다. 화면에서 값을 바꾸는 조작과 기준점 기록 버튼은 자동 시험(가짜 프레임)으로만 확인했습니다.

### 단계 6 — 원격 제어

명령 목록과 응답 형식은 사용자 문서 [remote.md](remote.md)에 있습니다.

| 항목 | 기준 |
| --- | --- |
| 방식 | `std::net` TCP, 한 줄에 명령 하나, 명령마다 `OK ...` 또는 `ERR ...` 한 줄 응답. 별도 크레이트 없음 |

| 제외 | FFC와 셔터 모드(규칙 4: 렌즈를 가렸는지 사람이 확인), 기준점 기록, Box/Line 편집, 경보 규칙 편집 |
| 실행 위치 | UI 스레드의 `logic` 단계(`app/remote.rs`). 화면 조작과 같은 함수를 쓰므로 같은 제약을 받음(CSV 기록 중 보정 잠금, 재생 중 녹화 불가) |
| 측정 번호 | 원격 `SPOT CLEAR`는 번호를 처음부터 다시 매기지 않음. 같은 처리 단계에서 지우고 다시 만든 Spot이 옛 경보 규칙을 물려받지 않게 하기 위함 |
| 제한 | 연결 4개, 한 줄 256바이트, 응답 대기 3초, 쓰기 타임아웃 2초 |

이 단계에서 프레임 처리를 `ui`에서 `logic`으로 옮기고 최신 1장 슬롯을 대기열로 바꿨습니다(5절). 이전에는 창을 최소화하면 프레임 처리가 멈춰 CSV·녹화·경보가 중단됐습니다. 슬롯만 둔 채 `logic`으로 옮겼을 때는 최소화 중 91프레임 중 5프레임이 빠졌습니다.

2026-11-25 실제 카메라 확인(임시 설정, 127.0.0.1:7700):
- 명령 20개를 차례로 보내 모두 기대한 응답을 받았습니다. 응답 시간은 창이 보일 때 1~50 ms였습니다. `FFC`는 알 수 없는 명령으로 거부됐고, CSV 기록 중 방사율 변경은 오류로 막혔습니다.

- 화면의 원격 제어 항목은 헤드리스 UI 시험으로만 그려 봤고, 실제 창에서는 직접 보지 않았습니다.

| 형식 | 736×480(H.264가 다루기 쉬운 16의 배수), H.264 High, 평균 2 Mbps, BT.601 제한 범위 NV12 입력. 컨테이너 MP4 |
| 시각 | 프레임마다 실제 도착 시각(재생 중이면 녹화 시각)을 씀(가변 프레임 간격). 시각이 뒤로 가면(재생 중 되감기) 그 프레임만 이전 프레임 + 1/9초로 두고 기준을 다시 잡아, 이후 프레임은 실제 간격을 유지(`video::Timeline`). 예전에는 시계가 따라잡을 때까지 모든 프레임이 1/9초 간격이 되어 영상이 느려졌음 |
| 대기열 | UI → 쓰기 스레드 대기열은 32장까지(4배 영상 포함 약 100 MB). 인코더가 밀리면 넘치는 프레임을 건너뛰고 세어, 끝날 때 "N프레임 건너뜀"으로 알림. 메모리가 끝없이 늘지 않게 함 |
| 대상 | 새로 표시되는 프레임마다 1장. 실시간과 재생 모두 녹화 가능(`.tvseq` → MP4 내보내기). 영상 출처가 바뀌면(재생 열기·닫기) 녹화를 끝냄. 일시정지 중에는 기록하지 않음 |
| 끝내기 | 중지, 앱 종료 시 파일을 마무리(`Finalize`). 앱이 강제 종료되면 파일을 재생할 수 없음 |
| 오류 | 시작 실패(Media Foundation 없음 등)는 바로 알림. 녹화 중 인코더 오류는 녹화를 멈추고 알림 |
| 원격 | `MP4 START`/`MP4 STOP`, `STATUS`의 `mp4=` |
| 빈 녹화 | 프레임 없이 멈추면 Media Foundation이 마무리를 거부하므로(0xC00D4A44) 파일을 지우고 "기록된 프레임 없음"으로 알림 |

2026-11-25 실제 카메라 확인(임시 설정, 창 최소화, 원격 명령으로 조작):

- 녹화 파일을 Windows 디코더로 다시 풀어 확인했습니다(저장소 밖의 임시 검사 도구). H.264 High, 736×480, 169프레임 모두 디코딩됐고 시각은 계속 증가했습니다. 풀어낸 프레임에서 시각, Spot, Box, Line, 최고·최저 표식, 색 막대가 화면과 같은 자리에 그려진 것을 확인했습니다.

### 단계 8 — 웹캠 합성

일반 카메라(웹캠) 영상을 열화상과 겹쳐, 뜨거운 곳이 실제 물체의 어디인지 알아보기 쉽게 합니다.

| 항목 | 기준 |
| --- | --- |
| 방식 | 겹치기: 웹캠 영상 위에 열화상을 반투명하게 그림(열화상 불투명도 0~100%, 기본 50%). 윤곽: 열화상 위에 웹캠 영상의 윤곽선(Sobel)을 흰 선으로 그림(진하기 0~100%, 기본 80%) |
| 좌표 | 화면과 측정은 계속 열화상 화소(160×120) 기준. 웹캠 영상을 열화상 화면에 맞춰 늘이고 옮김. Spot·Box·Line·경보·CSV는 바뀌지 않음 |
| 정렬 | 크기(열화상 폭 대비 0.5~3배, 웹캠 가로세로 비 유지), 가로·세로 위치(화면 폭·높이의 ±50%). 두 카메라 위치가 달라(시차) 한 거리에서만 정확히 맞음을 화면에 안내 |
| 자동 정렬 | "자동 정렬" 버튼(원격 `ALIGN`). 보이는 열화상(돌린 뒤)과 최신 웹캠 영상의 윤곽 방향을 비교해 크기·위치를 찾음(`src/webcam/align.rs`, 순수 함수). 윤곽은 Sobel 기울기를 각도를 두 배로 한 벡터(길이 g/(g+평균))로 나타내 3×3 흐림: 밝→어둠과 어둠→밝이 같고, 두 카메라에 함께 보이는 외곽선만 더해지며 한쪽에만 있는 무늬(벽돌, 옷 주름)는 평균 0. 일치도 = Σa·b/√(Σ\|a\|²Σ\|b\|²). 폭 40 화소에서 모든 크기(1.04배 간격)·위치를 찾고, 서로 다른 상위 6개를 폭을 두 배씩 늘리며(최대 원래 크기) 주변 ±3화소·크기 ±3단계로 다듬음. 웹캠이 열화상의 절반 이상을 덮어야 함. 일치도 0.25 미만이면 정렬을 바꾸지 않고 안내. 버튼은 별도 스레드(P3 256×192에서 release 약 0.6초), 원격은 UI 스레드에서 바로 실행. 처음에 쓴 윤곽 세기 상관은 웹캠에만 있는 무늬에 끌려 틀린 곳을 찾았음 |
| 수신 | Media Foundation Source Reader(`src/webcam/mf.rs`, unsafe). 장치가 주는 형식 중 가로 640에 가장 가까운 것을 골라 RGB32로 변환받음. 별도 스레드에서 동기 `ReadSample`, 최신 1장만 보관. 윤곽은 이 스레드에서 미리 계산 |
| 장치 | 목록에서 선택. 이름과 장치 경로(symbolic link)를 설정에 저장하고, 켜 둔 채 종료했으면 다음 실행 때 다시 연결. 목록 조회는 UI를 멈추지 않도록 별도 스레드. PureThermal은 WinUSB 드라이버라 목록에 나오지 않음 |
| 오류 | 열기 실패·연결 끊김은 상태를 표시하고 스레드를 끝냄(자동 재연결 없음, 다시 켜면 재시도). 접근 거부(0x80070005)는 Windows 개인 정보 설정의 카메라 권한을 안내 |
| 대상 | 실시간 영상에만. 재생 중에는 합성하지 않음(`.tvseq`에 웹캠 영상이 없으므로 다른 시각의 장면이 겹치는 것을 막음) |
| MP4 | 화면과 같은 방식으로 합성해 녹화 |
| 스냅샷 | 컬러 PNG와 16비트 PNG는 지금처럼 열화상만. 합성 중이면 웹캠 사진을 `_webcam.png`로 원래 해상도로 따로 저장하고, JSON에 장치 이름·방식·정렬값을 기록 |
| 원격 | `ALIGN`(자동 정렬)만 |

2026-11-28 자동 정렬 확인(P3 256×192, 180° 돌림 + Logitech C920 640×480, 사람이 약 0.5 m 앞): 스냅샷 한 쌍에 `examples/webcam_align`으로 크기 1.352, 가로 −0.027, 세로 +0.089, 일치도 0.44를 찾았고 합성 결과에서 턱·목둘레·어깨선이 겹침. 같은 쌍에서 열화상을 위아래로 뒤집으면 일치도 0.16(믿지 않음). 눈대중 값(1.17, −0.03, +0.08)은 0.23이었음. 앱에서 원격 `ALIGN`으로 실행(사람 없이 방 안, 1~3 m): 크기 1.418, 가로 −0.025, 세로 −0.010, 일치도 0.29로 적용됐고, 같은 때 찍은 스냅샷 한 쌍에서 장, 의자 등받이, 장 위 병들의 위치가 열화상 1~4화소 안에서 맞음. 화면 캡처로는 확인하지 못함(다른 창이 앞에 있었음).

2026-11-26 실제 장치 확인(노트북 내장 USB2.0 HD UVC WebCam, `examples/webcam`, 임시 설정으로 앱 최소화, 원격 명령으로 조작):
- 장치 목록 조회 6 ms, 640×480 RGB32로 열림, 첫 영상까지 약 0.65초, 끄기 약 0.3초. 이 웹캠은 2-D 버퍼 없이 위에서 아래로 쌓인 버퍼(stride +2560)를 줌.
- 웹캠을 켠 채로 열화상 수신 8.9 fps 유지. 스냅샷에 `_webcam.png`(640×480)와 JSON의 `webcam` 항목이 기록됨.
- 겹치기 50%로 녹화한 MP4(55프레임)를 다시 풀었더니 영상 부분 평균 밝기가 47.4로, 열화상만일 때(91.5)의 절반에 글자 표시가 더해진 값이었음(웹캠 쪽 평균 0.5).
- 시험할 때 웹캠 앞이 어두워(최대 밝기 15, 웹캠 속도 7~12 fps) 영상 방향, 정렬, 윤곽 방식은 실제 장면으로 확인하지 못했고 자동 시험으로만 확인함. 화면 표시와 설정 항목도 아직 직접 보지 않음.

### 단계 9 — Thermal Master P3

Thermal Master P3(VID 0x3474, PID 0x45A2)는 UVC가 아니라 제조사 전용 USB 프로토콜을 씁니다. 프로토콜은 공개 역공학 자료 [jvdillon/p3-ir-camera](https://github.com/jvdillon/p3-ir-camera)의 `P3_PROTOCOL.md`(Apache-2.0)와 [xaionaro-go/thermalmaster](https://github.com/xaionaro-go/thermalmaster)의 문서를 근거로 새로 구현했습니다(코드는 복사하지 않음).

| 항목 | 기준 |
| --- | --- |
| 장치 | 인터페이스 0(제어)과 1(alt 0 정지, alt 1 bulk IN 0x81). Windows에서 WinUSB 드라이버가 붙어 있어야 함 |
| 명령 | 18바이트: 종류(2, 큰 엔디언), 파라미터(2), 레지스터(2), 0×6, 응답 길이(2), 0×2, CRC16-CCITT(초기값 0, 0~15바이트, 작은 엔디언). 보낸 뒤 상태 1바이트(0xC1/0x22)를 읽고, 응답이 있으면 0xC1/0x21로 읽은 뒤 상태를 다시 읽음 |
| 시작 | start_stream 명령 → 1초 → 인터페이스 1 alt 1 → 0x40/0xEE(wIndex 1) → 2초 → bulk 읽기 1회(버림) → start_stream 다시. 대기 중에도 정지 요청을 확인 |
| 정지 | 인터페이스 1 alt 0, 인터페이스 해제 |
| 프레임 | 시작 표식(12바이트, 0x0C + 0x8C/0x8D) + 화소 256×386×2바이트 + 끝 표식(12바이트 단독 전송, 0x8E/0x8F). 두 표식의 카운터(cnt1)가 같을 때만 사용. 화소의 0~191행은 장치가 밝기 조정한 IR 영상, 192~193행은 메타, 194~385행이 온도(1/64 K) |
| 읽기 | 16 KiB씩 bulk 읽기(500 ms 타임아웃)해 이어 붙임. 한 번에 프레임 크기만큼 읽으면 Windows에서 장치 오류가 난다는 보고가 있어 따름. 12바이트 읽기가 프레임 끝. 크기가 맞지 않거나 표식이 틀리면 버리고 다음 시작 표식부터 다시 맞춤(셔터 직후의 비정상 프레임도 여기서 버려짐) |
| 온도 | `kelvin_per_count` = 1/64. 앱의 방사율·기준점 보정, 측정, 기록은 Lepton과 같은 경로 |
| 감도 | 명령을 보내지 않고 카메라 기본값(고감도, −20~150 °C)을 씀. 저감도는 공식 앱이 "100~600 °C"로 표시하는 범위임([Thermal-Inspector](https://github.com/trytuna/Thermal-Inspector)의 `docs/HARDWARE-NOTES.md`: 공식 앱의 범위 전환이 USB 감도 명령과 같은 명령). 2026-11-27 실측(펌웨어 .17, `examples/p3gain`): 실내 장면에서 저감도는 약 19.6 °C 아래가 일정한 값(15298, −34 °C)으로, 20~35 °C는 고감도 64 counts/K 대신 약 14 counts/K로 나옴. 즉 범위 아래의 장면은 맞지 않음. 100 °C 이상에서 1/64 K로 맞는지는 뜨거운 물체(다리미, 인두)로 확인이 남아 있음. 같은 측정에서 감도를 13번 바꿔도 버린 프레임 0, 약 1초 안에 안정됨. 예전 기록(전환마다 버린 프레임 130장 이상, `sys gain switch error`)은 연결할 때마다 감도 명령을 보내던 때의 것. `p3::Gain`·`set_gain`은 실험용으로만 남김(`examples/p3 low|high`, `examples/p3gain`) |
| 셔터 | P3는 셔터가 있고 약 90초마다 스스로 보정함. "셔터 보정" 버튼은 확인 없이 바로 명령을 보냄(규칙 4는 셔터 없는 Lepton에만 해당). 원격 명령에는 넣지 않음 |
| 카메라 선택 | 설정의 카메라 종류: 자동(PureThermal을 먼저 찾고 없으면 P3), PureThermal, P3. 바꾸면 지금 연결을 끊고 새 종류를 찾음 |
| 상태 폴링 | 없음(P3에는 FPA 온도 등 읽을 명령이 알려지지 않음) |
| 정지 감지 | 5초(Lepton은 2초). P3는 셔터 보정 중 최대 약 1.7초 동안 쓸 수 있는 프레임을 보내지 않고, 이때 다시 열면 더 나빠짐 |
| 예열·보정 중 전송 | 켠 뒤 약 1~2분과 셔터 보정 중에는 끝 표식 없는 204,800바이트 전송이 이어짐(시작 표식 카운터 0, 프레임 경계가 전송 경계와 맞지 않음). 해독하지 않고 버림. 참고 자료의 '셔터 직후 프레임 재조립' 모양(204,800 + 2,060 + 12)은 이 PC에서 관찰되지 않아 구현하지 않음 |
| 부하 | 초당 약 25장. 시퀀스 녹화는 Lepton 기준(약 0.58 GB/시간)보다 약 7배 커질 것으로 예상. MP4는 4배 확대해 1120×768 |

2026-11-27 실제 장치 확인(P3, 펌웨어 00.00.02.17):
- `examples/p3` 10초: 장치 열기 50 ms, 시작 순서 3.5초, 25.00 fps, 버린 프레임 0, 가장 긴 간격 52 ms. 온도 15~22 °C(실내).
- 셔터 보정 명령: 셔터가 닫힌 약 0.8초 동안 프레임이 없고, 직후 비정상 프레임 2장을 버린 뒤 정상 수신. 2초 정지 감지에 걸리지 않음.
- 앱(임시 설정, 카메라 종류 P3, 최소화, 원격 명령): 25.0 fps, 화소 온도·Spot·스냅샷(256×192 컬러·16비트 PNG, JSON `kelvin_per_count` 0.015625, 장치 "P3")·MP4(6초에 154프레임) 정상. CPU는 코어 하나의 약 10%.
- 화면의 카메라 종류 선택과 P3 설정 항목, 실행 중 종류 전환, P3 USB 분리는 아직 직접 확인하지 않음.
- **이상 상태:** 감도 명령을 연결마다 보내던 때, 앱을 여러 번 열고 닫은 뒤 영상이 깨지다 2초 정지 판정으로 다시 열기를 반복했고, 이후 시작 명령에는 정상 응답(0x01)하지만 bulk 데이터를 전혀 보내지 않게 됨. libusb 리셋, clear halt, 감도 명령 생략으로는 풀리지 않았고 다시 꽂아야 풀림. 감도 명령 → 비정상 전송 → 2초 정지 판정 → 다시 열기의 반복이 유력한 원인이라 감도 명령을 없애고 P3 정지 판정을 5초로 늘림. 수정 후 앱을 연속 3번 열고 닫아도 매번 25.0 fps, 버린 프레임 0. 세션 끝에 버린 프레임의 이유(크기·카운터·초과)와 카메라 내부 로그(상태 레지스터 긴 읽기)를 기록함. 시작 순서의 clear halt는 해가 없어 남겨 둠.

### 단계 15 — 경보 확장, 측정 차의 기록 (2026-11-28)

기능 후보(§10)의 "경보 동작의 나머지"와 "측정의 차를 경보·CSV·그래프 대상으로"를 넣었습니다. 소리는 Win32 호출(`unsafe`)이 필요해 넣지 않았습니다(작업 표시줄 깜박임은 그대로).

| 항목 | 기준 |
| --- | --- |
| 범위 밖 조건 | 규칙 조건에 "범위 밖" 추가: 값 < 아래 한계 또는 > 위 한계. 두 한계는 어느 쪽에 적어도 됨. 해제는 양쪽 한계에서 해제 폭만큼 안쪽으로 들어왔을 때. 범위가 해제 폭의 두 배보다 좁으면 가운데에서 해제. 예전 규칙(위 한계 없음)을 "범위 밖"으로 바꾸면 위 한계 = 기준 + 10 |
| 차 감시 | 규칙에 "−" 항목: 다른 측정을 고르면 (왼쪽 − 오른쪽)을 감시. 둘 중 하나라도 지워지면 규칙도 지움. 입력 범위는 차를 감시할 때 ±640 °C(평소 −40~600). 설정 파일의 `minus`, `upper`가 없는 예전 규칙은 그대로 읽힘 |
| 경보 중 MP4 녹화 | 켜면 경보가 발생했을 때 MP4 녹화를 시작하고, 모든 경보가 해제된 뒤 정한 시간(기본 10초)이 지나면 끝냄. 이미 녹화 중이면 그 녹화를 건드리지 않음. 사용자가 멈추면 다음 경보까지 다시 시작하지 않음. 발생 전 영상은 담기지 않음(앞 구간을 담으려면 프레임을 계속 쌓아 둬야 해서 넣지 않음). 원격 `ALARMS`에 `mp4=alarm` |
| 경보 기록 파일 | 켜면 발생·해제·감시 중단·재개를 저장 폴더의 `alarm_log.csv`에 한 줄씩 덧붙임(`time,event,rule,value_C`, UTF-8 BOM). 사건마다 파일을 열고 닫으므로 앱이 켜져 있어도 열어 볼 수 있음. 실패는 경보 기록에 한 번만 알림. 측정을 지워 규칙이 없어진 것은 적지 않음 |
| 측정 차의 CSV | 기록을 시작할 때 있던 차마다 열 하나(`화면최고-S1_C`처럼 공백 없이). 값이 없으면 빈 칸 |
| 측정 차의 그래프 | 시간 그래프에 점선으로, "측정 차" 체크(기본 켬). 같은 세로축(°C)이라 0 근처의 선이 온도 선과 함께 보임 |

MP4 마무리 제한 시간: 시험 중 한 번, 종료할 때 MP4 기록 스레드가 Media Foundation `IMFSinkWriter::WriteSample` 안에서 돌아오지 않아 앱이 닫히지 않았습니다(cdb로 스택 확인. 인코더 스레드는 모두 쉬는 중, MF 작업 큐 대기 없음). 같은 조건(최소화, 가려진 창, 녹화 중 `SCREENSHOT`, 약 1분 녹화 뒤 종료)으로 세 번 다시 해 보았으나 재현되지 않았고, 다른 스레드의 `MFShutdown`도 원인이 아니었습니다(시험으로 확인). 원인은 찾지 못했습니다. 그래서 `Mp4Writer::finish`와 drop이 기록 스레드를 최대 15초만 기다리게 했습니다. 넘으면 그 스레드를 두고 진행하며 오류("the encoder did not finish within 15 s; the file is incomplete")를 알립니다. 그 파일은 재생되지 않습니다.

확인(2026-11-28, P3 실시간, 임시 설정 파일로 띄우고 끝난 뒤 원래 파일로 되돌림):

- 규칙 셋(S1 − 중앙 −100 이상, 중앙 0~100 범위 밖, 중앙 50~60 범위 밖)에서 `ALARMS`가 `mp4=alarm R1=active R2=clear R3=active`. 화면에서 경보 띠의 "중앙 50.0~60.0 °C 범위 밖", 자동 시작된 MP4, 시간 그래프의 점선 "Δ 화면 최고 − 중앙"을 봄(원격 `SCREENSHOT`).
- `SPOT DEL 1` → R1이 지워지고 R3이 남아 녹화는 계속. `MP4 STOP` 뒤 `mp4=alarm`이 사라지고 다시 시작하지 않음.
- CSV의 차 열: `화면최고-중앙_C` = 29.66 − 24.49 = 5.17. `alarm_log.csv`는 여러 번 실행해도 머리줄 하나 아래로 이어짐.
- 녹화 중 종료 네 번: 모두 MP4가 마무리됨(`moov` 있음).
- 찾아 고친 것: 차 규칙의 기준값 −100이 입력 칸의 범위(−40~600)에 잘려 −40으로 바뀜 → 차를 감시할 때는 ±640.
- 자동 시험으로만 확인: 해제 뒤 지정 시간이 지나 녹화가 끝나는 것(실제 장면에서 경보를 해제시켜 보지 않음), 규칙 편집기가 280 pt 폭 안에 들어가는 것(실제 창의 경보 구역은 보지 못함: 사용자가 작업 중이라 창을 앞으로 가져오지 않았고, 완전히 가려진 창은 그려지지 않음).

## 7. 코드 규칙

- `unsafe`는 `crates/libuvc-sys`, `src/camera/uvc.rs`, `src/video/mf.rs`·`src/webcam/mf.rs`(Media Foundation COM 호출)에만 둡니다. 각 `unsafe` 블록 위에 안전 조건을 주석으로 적습니다. 외부 코드를 그대로 가져온 `crates/winit`은 이 규칙의 대상이 아닙니다.
- 캡처·제어 경로에서 `unwrap`/`expect` 금지. 오류는 `anyhow::Result` 또는 전용 오류 타입으로 UI까지 올려 상태 줄에 표시합니다.
- `thermal/` 모듈은 장치 없이 테스트할 수 있어야 합니다(순수 함수). 팔레트, 범위, 통계, Spot 계산에 단위 테스트를 둡니다.
- 커밋 전: `cargo fmt`, `cargo clippy --all-targets`(경고 0 목표), `cargo test`.
- UI 문자열은 한국어를 기본으로 합니다. 폰트는 Windows의 `malgun.ttf`를 실행 시 읽어 egui에 추가합니다(없으면 기본 폰트).

## 8. 빌드와 실행

```powershell
cargo build --release
.\target\release\thermalview.exe
# 수신 검증
cargo run --release --example grab
# 웹캠 확인(영상은 저장하지 않고 크기·속도·밝기만 출력)
cargo run --release --example webcam
# Thermal Master P3 수신 확인(장치 정보, fps, 버린 프레임, 온도 범위)
cargo run --release --example p3
# 업스케일 비교: 스냅샷의 16비트 PNG로 센서 화소 | 없음 | 보통 | 강하게를 나란히 저장
cargo run --release --example upscale <파일_raw16.png> [출력.png]
# 웹캠 자동 정렬: 합성 중 찍은 스냅샷 한 쌍으로 정렬값·일치도를 출력하고 겹친 그림을 저장.
# 끝에 크기 가로 세로를 주면 그 정렬의 일치도도 출력
cargo run --release --example webcam_align <파일_raw16.png> <파일_webcam.png> <출력.png> [scale dx dy]
# PureThermal 프레임 간격(끊김) 측정: [초] [상태 조회 간격 ms, 0=조회 없음]
cargo run --release --example gaps 120 5000
```

사전 조건: Visual Studio Build Tools(C 컴파일러), PureThermal에 WinUSB 드라이버(Zadig: Options > List All Devices, "Ignore Hubs or Composite Parents" 해제 후 Composite Parent에 설치).
환경 변수 `LIBUVC_TRACE=1`(프레임) / `2`(패킷)로 vendor libuvc의 진단 출력을 켤 수 있습니다.

## 9. 장비 시험 절차

1. GetThermal 등 카메라를 쓰는 프로그램을 모두 닫습니다.
2. `cargo run --release --example grab` → fps ≥ 8.5 확인.
3. 앱 실행 → 영상, 최고·최저 표시, Spot 측정 확인.
4. 셔터 모드 MANUAL 선택 → 앱 재시작 → MANUAL 유지 확인.
5. 렌즈를 가리고 FFC → 잔상 없음 확인.
6. 스트리밍 중 USB 분리 → 안내 표시 → 다시 연결 → 자동 복구 확인.
7. 스냅샷 → PNG 두 장과 JSON 생성, 16비트 PNG 값/100 − 273.15가 화면 Spot 값과 일치하는지 확인.
8. 1시간 연속 실행 후 fps와 메모리 확인.

### 기능 후보 (2026-11-28 조사)

다른 열화상 프로그램과 비교해 없던 기능입니다. 비교 대상은 공개 뷰어(Thermal-Inspector, OpenRMH-IRCAM, thermal-camera-viewer, p3-ir-camera 등의 README·문서)와 상용 도구(FLIR Thermal Studio 기능표, HIKMICRO Analyzer 자료, Optris PIX Connect 소개)입니다. 크기는 코드를 읽고 어림한 값입니다(S: 약 150줄 이하·새 의존성 없음, M, L).

단계 13에서 넣은 것: 등온선, 시간 잡음 필터, 화면 정지, 스냅샷 다시 열기, 전체 화소 온도 CSV, CSV 기록 간격과 간격 스냅샷, 경보 발생 시 스냅샷, 두 측정의 차(표시와 스냅샷 JSON), 영역·선 통계의 시간 그래프, 확대·이동, 극단값 제외 자동 범위, 팔레트 뒤집기, 영역 안 최고 표식, 클립보드 복사. 단계 14에서 넣은 것: 차이 영상. 단계 15에서 넣은 것: 범위 밖 경보, 측정 차의 경보·CSV·그래프, 경보 중 MP4 녹화, 경보 기록 파일.
